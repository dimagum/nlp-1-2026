# 18. Retrieval-Augmented Generation (RAG)

> [!summary] Суть
> - **RAG**: LLM отвечает, опираясь на документы, найденные поиском по внешней базе знаний. Три шага: **retrieve** → **augment** (вставить найденное в промпт) → **generate**.
> - **Зачем**:
>   - знания модели устаревают (knowledge cutoff);
>   - модель галлюцинирует;
>   - нужны приватные и корпоративные данные;
>   - нужны ссылки на источники;
>   - знания хочется обновлять без переобучения.
> - **Компоненты**:
>   1. индексация: загрузка, чанкинг, эмбеддинги, векторная БД + инвертированный индекс;
>   2. обработка запроса: переформулировка;
>   3. **retriever**: dense, sparse или гибрид;
>   4. **reranker**: cross-encoder;
>   5. сборка промпта;
>   6. **LLM-генератор** со ссылками на источники.
> - **Гибридный поиск** = dense (смысл, перефразы) + sparse/BM25 (точные совпадения: коды, имена, номера, редкие термины). Они ошибаются на разных запросах, поэтому вместе надёжнее. Результаты объединяют, например, через **RRF**.
> - **Оценка**: отдельно **поиск** (Recall@k, MRR, nDCG), отдельно **генерация** (faithfulness, answer relevance, correctness) и **end-to-end**. Инструменты: RAGAS, LLM-as-judge; плюс задержка и стоимость.

> [!tip] Интуиция
> **Экзамен с открытой книгой.** LLM без RAG — студент, отвечающий по памяти: может уверенно выдумывать. В RAG студенту разрешили сходить в библиотеку:
> - библиотекарь (retriever) приносит стопку подходящих книг;
> - ассистент (reranker) отбирает самые нужные страницы;
> - студент отвечает по ним и ссылается на источники.
>
> **Гибридный поиск — два библиотекаря.** Один понимает смысл: на запрос «книги про болезни сердца» принесёт и «Кардиологию». Другой ищет буквально по каталогу: «ГОСТ 7.32-2017» найдёт точно.

## Подробнее

### Пайплайн
```
Offline:  документы → парсинг/очистка → чанкинг → эмбеддинги → индексы (векторный + BM25)

Online:   запрос → (переформулировка / HyDE) → поиск top-k (dense ∪ sparse)
                 → слияние (RRF) → rerank → top-n чанков → промпт → LLM → ответ + ссылки
```

### Компоненты
1. **Загрузка и парсинг**: PDF, HTML, таблицы. На практике это частый источник ошибок.
2. **Чанкинг**:
   - фиксированный размер с перекрытием (например, 300–1000 токенов, перекрытие 10–20%);
   - по структуре документа (заголовки, абзацы);
   - семантический.

   К чанкам добавляют **метаданные** (источник, дата, раздел) для фильтров и цитирования. Компромисс: маленькие чанки дают точный поиск, но мало контекста; большие — наоборот.
3. **Embedding-модель (bi-encoder)**: $s(q,d)=\cos\big(E_q(q),\,E_d(d)\big)$. Документы кодируются заранее. Примеры: E5, BGE, multilingual-e5 для русского.
4. **Векторный индекс**: приближённый поиск ближайших соседей (HNSW, IVF-PQ). Инструменты: FAISS, Qdrant, Milvus, pgvector.
5. **Sparse retriever**: BM25 по инвертированному индексу ([[02 Счётные эмбеддинги и BM25]]), например Elasticsearch или OpenSearch. Есть и обучаемые разреженные модели, например SPLADE.
6. **Reranker (cross-encoder)**: $s(q,d)=f([q;\,d])$. Запрос и документ подаются вместе, с полным вниманием между ними, поэтому точнее, но дорого. Применяют только к top-50–100 кандидатам.
7. **Обработка запроса**: переформулировка с учётом истории диалога, разбиение на подвопросы, multi-query, **HyDE** (сгенерировать гипотетический ответ и искать по нему).
8. **Генератор**: промпт вида «Отвечай только по контексту; если ответа там нет, скажи «не знаю»; укажи источники».

Развитие: agentic RAG (модель сама решает, когда и что искать), GraphRAG, итеративный поиск.

### Гибридный поиск: зачем
| Запрос | Dense | BM25 |
|---|---|---|
| «как вернуть деньги за билет» → документ «Правила возврата средств» | ✅ смысл совпадает | ❌ другие слова и формы |
| «ошибка E-1042 в контроллере» | ❌ код размывается в эмбеддинге | ✅ точное совпадение |
| «ст. 159 УК РФ» | ❌ числа плохо различаются | ✅ |
| Артикулы, ФИО, аббревиатуры, новые термины, которых не было в обучении embedding-модели | ❌ | ✅ |
| Опечатки, синонимы, запрос на другом языке | ✅ | ❌ |

**Слияние результатов:**
- **Reciprocal Rank Fusion** (используются только ранги, калибровать скоры не нужно):
$$\text{RRF}(d)=\sum_{r\in\text{retrievers}}\frac{1}{k+\text{rank}_r(d)},\qquad k=60$$
  Пример: документ на 1-м месте в dense и на 3-м в BM25 получает $\frac1{61}+\frac1{63}\approx0.0323$.
- **Взвешенная сумма нормированных скоров**: $s=\alpha\,\tilde s_{dense}+(1-\alpha)\,\tilde s_{BM25}$ после min-max нормировки; $\alpha$ подбирают на валидации.

### Как оценивать RAG
**1. Поиск** (нужна разметка: какие чанки релевантны каждому запросу):
- **Recall@k** — доля релевантных документов, попавших в top-k; **Hit rate@k** — нашёлся ли хоть один.
- **Precision@k** — доля релевантных среди top-k.
- **MRR**: $\frac{1}{\lvert Q\rvert}\sum_{q}\frac{1}{\text{rank}_q}$, где $\text{rank}_q$ — позиция первого релевантного документа.
- **nDCG@k**: $\text{DCG@}k=\sum_{i=1}^{k}\frac{2^{rel_i}-1}{\log_2(i+1)}$, $\text{nDCG}=\text{DCG}/\text{IDCG}$. Учитывает градации релевантности и позиции.

**2. Генерация:**
- **Faithfulness / groundedness**: подтверждается ли каждое утверждение ответа контекстом. Ловит галлюцинации.
- **Answer relevance**: отвечает ли ответ на заданный вопрос.
- **Correctness**: совпадение с эталоном (EM/F1, семантическая близость, LLM-as-judge).
- **Context precision / context recall** (RAGAS): насколько найденный контекст точен и полон относительно эталонного ответа.
- **Точность цитирования**: действительно ли указанный источник подтверждает утверждение.

**3. Система целиком:**
- задержка и стоимость;
- **negative rejection**: говорит ли «не знаю», когда ответа в базе нет;
- устойчивость к шумным и нерелевантным чанкам;
- A/B-тесты и обратная связь пользователей.

**Откуда взять тестовый набор:**
- ручная разметка троек «вопрос – ответ – источник»;
- **синтетика**: LLM генерирует вопросы по чанкам, и правильный чанк заранее известен;
- логи реальных запросов.

**Диагностика по компонентам:** если recall поиска низкий, проблема в поиске или чанкинге. Если recall высокий, а ответ плохой, проблема в промпте или генераторе.

> [!question]- Доп. вопросы
> - **RAG или fine-tuning?** RAG — для **знаний** (факты, частые обновления, нужны ссылки). Fine-tuning — для **поведения** (стиль, формат, специфические навыки). Часто их совмещают.
> - **Почему не засунуть все документы в длинный контекст?** Это дорого и медленно, качество падает на середине длинного контекста («lost in the middle»), а база может не поместиться.
> - **Bi-encoder vs cross-encoder?** Bi-encoder быстрый (векторы документов считаются заранее) и нужен для первичного поиска. Cross-encoder точный, но медленный, поэтому его используют для переранжирования.
